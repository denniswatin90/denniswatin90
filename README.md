## How I work

**Integrity tests before balance tests.** "The group is out by 847,500" is true
and useless. "Account 50999 has no group mapping" names the fix. Same defect,
five minutes versus two days.

**Every check returns the failing rows**, never a boolean. One query gives you
the verdict, the size of the problem, and a sample to hand the data owner.

**Bad rows are quarantined with a reason, never deleted.** Dropping failures is
how a completeness metric stays at 100% while the warehouse loses records.

**Every dedupe `ORDER BY` is a total order.** A value that moves between runs
with no code change is worse than one that is consistently wrong, because the
investigation starts in the wrong place.

**Accuracy is the one dimension you cannot test in isolation.** Everything else
can be asserted against the data itself, which only establishes internal
consistency. Accuracy needs an authority outside the platform — which is why
reconciliation is worth more than fifty row-level rules.

## What I got wrong

Each repository has a section with this title, because a portfolio of clean
successes reads as either inexperienced or not entirely honest. A few:

- Adding PHP movements to USD movements across a functional currency change
  produced a **$97 million** break in a $130 million balance sheet, with every
  individual number correct. IAS 21.35 requires a rebase at the rate on the date
  of change.
- Normalising a join key turned a unique dimension into a non-unique one.
  **61,507 sessions became 208,493** with no error — and the first test to fail
  was an unrelated one three joins downstream.
- Summing cycle-count variance reported **three times** the true shrinkage,
  because the system never posted adjustments and the same missing case was
  re-found every month.
